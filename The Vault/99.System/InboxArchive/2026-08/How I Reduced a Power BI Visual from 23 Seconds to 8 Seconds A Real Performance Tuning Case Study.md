*A slow Power BI report isn’t always caused by complex DAX or massive datasets. Sometimes, the biggest performance bottleneck is hidden in a single default setting.*

As Power BI developers, we’ve all heard the same feedback from business users:

***“The dashboard is slow.”***

But where do you start?

Do you optimize DAX? Redesign the data model? Tune SQL queries? Or could the real issue be hiding somewhere you least expect?

Recently, I worked on a production Power BI report where an **Account Table** visual took more than **23 seconds** to load. Interestingly, the rest of the dashboard was responsive, making this one visual the obvious bottleneck.

Rather than making random changes, I followed a structured performance diagnosis process to identify the true root cause.

This article walks through that investigation step by step.

## The Challenge

The report was actively used by business users, and waiting over 20 seconds for a single visual significantly affected the overall user experience.

The goal wasn’t simply to make the report faster.

The objective was to understand **why** the visual was slow, identify the actual bottleneck, and validate the solution with measurable results.

## Step 1 — Measure Before You Optimize

One of the most important rules in performance tuning is:

**Never optimize what you haven’t measured.**

I started with **Performance Analyzer** in Power BI Desktop and refreshed the Account Table visual.

The results immediately narrowed the investigation.

**Performance Breakdown**

- **Total Visual Load:** 23.6 seconds
- **DAX Query:** 23.3 seconds
- **Visual Rendering:** Negligible

This confirmed that the delay wasn’t caused by rendering or formatting — it was almost entirely due to DAX query execution.

At this point, I knew the investigation needed to move beyond the report canvas.

## Step 2 — Analyze the Query in DAX Studio

The next step was to extract the generated DAX query and analyze it using **DAX Studio**.

To ensure accurate measurements, I:

- Cleared the cache
- Enabled **Server Timings**
- Captured the **Query Plan**
- Executed the query independently

This allowed me to inspect how the Power BI engine was processing the request without any visual overhead.

The results were surprising.

- **88.7%** of execution time was spent in the **Formula Engine**
- **1,033 Storage Engine queries**
- Only **17 rows** returned

That ratio immediately stood out.

Generating more than one thousand Storage Engine queries to return just seventeen rows isn’t typical behavior.

It indicated that the engine was repeatedly evaluating combinations rather than processing data efficiently.

## Step 3 — Read the Generated DAX Query

Many developers stop after reviewing Server Timings.

I decided to go one step further.

I carefully examined the generated DAX query line by line.

One section immediately caught my attention:

**\_\_DS0PrimaryShowAllCompat**

Inside this block, Power BI had generated nested **GENERATEALL** statements combined with multiple **OR(NOT(ISBLANK()))** conditions across every measure used in the visual.

This wasn’t handwritten DAX.

It was automatically generated by Power BI.

At that moment, the real root cause became clear.

## The Hidden Culprit

The **“Show items with no data”** option was enabled on one of the grouping fields.

Although this setting appears harmless, it forces Power BI to:

- Generate every possible category combination
- Perform unnecessary cross-joins
- Evaluate every measure for blank values
- Repeat those calculations thousands of times before returning the final result

The issue wasn’t caused by poorly written DAX.

It wasn’t the SQL query.

It wasn’t the data model.

It was a single visual setting creating unnecessary work for the Formula Eng

## The Fix

I disabled the **“Show items with no data”** option on the affected grouping field.

After making the change, I repeated the same Performance Analyzer and DAX Studio tests to validate the results.

## Results

MetricBeforeAfterVisual Load Time **23,599 ms8,741 ms** Performance Improvement — **~63% Faster**

Without rewriting any DAX measures or redesigning the data model, the visual became significantly faster and much more responsive for end users.

## What This Experience Reinforced

This project reminded me that performance optimization is rarely about making random adjustments.

A structured diagnostic approach consistently produces better results.

My workflow was simple:

1. Measure the problem.
2. Isolate the bottleneck.
3. Analyze the evidence.
4. Identify the root cause.
5. Validate the improvement.

Too often, we assume slow Power BI reports are caused by bad DAX, inefficient SQL, or large datasets.

Sometimes, the biggest performance gains come from understanding how Power BI generates queries behind the scenes.

## Key Takeaways

✅ Measure before optimizing.

✅ Let data guide your investigation instead of assumptions.

✅ Don’t assume DAX is always the problem.

✅ Read the generated DAX query — it often reveals hidden behavior.

✅ Small configuration changes can produce significant performance improvements.
